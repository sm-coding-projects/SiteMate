# SiteMate

Build-progress tracker for a Sydney residential builder. One Cloudflare Worker serves a React SPA and a Hono API,
backed by D1, R2 and Queues, with Clerk for auth. Everything runs on free tiers.

- Design & data model: [`docs/DESIGN.md`](docs/DESIGN.md)
- Visual design system: [`docs/DESIGN-SYSTEM.md`](docs/DESIGN-SYSTEM.md) → full spec in
  [`design-system/sitemate/MASTER.md`](design-system/sitemate/MASTER.md)

## Prerequisites

- Node 22+ and pnpm 10+
- A Cloudflare account (free plan), logged in with `pnpm wrangler login`
- A Clerk application (free Hobby plan) — use the **development** instance until there is a custom domain

## Project layout

```
src/client/   React SPA (Vite, TanStack Query, React Router, Tailwind v4, shadcn/ui)
src/worker/   Hono API under /api + Queue consumer
src/db/       Drizzle schema (D1 / SQLite)
src/shared/   Types shared by client and worker
migrations/   SQL migrations generated by drizzle-kit, applied by wrangler
```

## One-time setup

### 1. Cloudflare resources

```bash
pnpm wrangler d1 create sitemate-db --location oc
pnpm wrangler r2 bucket create sitemate-files --location oc
pnpm wrangler queues create sitemate-jobs
```

Copy the `database_id` printed by the first command into `wrangler.jsonc`, then run `pnpm cf-typegen`.

### 2. Clerk

In the [Clerk dashboard](https://dashboard.clerk.com) for the development instance:

1. **Configure → Restrictions → Sign-up mode: Restricted.** Users can only join by invitation.
2. **Configure → Sessions → Customize session token**, add these claims so the API can read the user's
   profile and role without calling Clerk on every request:
   ```json
   {
     "email": "{{user.primary_email_address}}",
     "name": "{{user.full_name}}",
     "role": "{{user.public_metadata.role}}"
   }
   ```
3. **Users → Invite** each person (or create them directly).

#### Making someone an admin

Open the user in **Users**, scroll to **Metadata → Public**, and set:

```json
{ "role": "admin" }
```

Anyone without `"role": "admin"` is a read-only **viewer**. Role changes take effect when the user's session
token refreshes (within about a minute) — or immediately after they sign out and back in.

### 3. Local environment files

```bash
cp .dev.vars.example .dev.vars   # Worker secrets: CLERK_SECRET_KEY, CLERK_PUBLISHABLE_KEY, …
cp .env.example .env             # SPA: VITE_CLERK_PUBLISHABLE_KEY
```

Fill in the keys from **Clerk → API keys**. Both files are git-ignored.

### 4. Production secrets and vars

```bash
pnpm wrangler secret put CLERK_SECRET_KEY
pnpm wrangler secret put CLERK_PUBLISHABLE_KEY
pnpm wrangler secret put AUTHORIZED_PARTIES   # e.g. https://sitemate.<subdomain>.workers.dev
```

`VITE_CLERK_PUBLISHABLE_KEY` must be in `.env` when you run `pnpm deploy`, because Vite inlines it at build time.

## Development

```bash
pnpm install
pnpm db:migrate:local   # apply migrations to the local D1
pnpm dev                # Vite + Worker runtime on http://localhost:5173
```

`pnpm dev` runs the SPA and the Worker together in the real Workers runtime, with local D1, R2 and Queues.
| Command | What it does |
|---|---|
| `pnpm typecheck` | TypeScript (client, worker and config projects) |
| `pnpm lint` / `pnpm format` | Biome |
| `pnpm db:generate --name <name>` | Generate a migration after editing `src/db/schema.ts` |
| `pnpm db:migrate:local` / `pnpm db:migrate:remote` | Apply migrations |
| `pnpm cf-typegen` | Regenerate binding types after editing `wrangler.jsonc` |

## Deploy

```bash
pnpm db:migrate:remote
pnpm deploy             # vite build + wrangler deploy → https://sitemate.<subdomain>.workers.dev
```

## API (step 1)

| Route | Auth | Purpose |
|---|---|---|
| `GET /api/health` | public | Liveness check |
| `GET /api/me` | signed in | Current user and role (lazily upserts the `users` row) |
| `POST /api/admin/queue-ping` | admin | Sends a test message to `sitemate-jobs`; the consumer logs it |

Watch the queue consumer with `pnpm wrangler tail`.

Write routes must use `requireRole("admin")` from `src/worker/middleware/auth.ts`.
